# gatylnia_bot

A Telegram bot for a small group of friends. It lives in a few group chats,
answers in Ukrainian, keeps score of in-jokes, rates the music people share,
and collects notes on the band's demo tracks.

It's a Rails 8.1 app with no UI: Telegram posts updates to a webhook, a
background job decides what to do with each one, and the bot answers through
the Bot API.

## What it does

Each chat has a **mode**, plus two features that can be switched on or off.

| | What it is |
|---|---|
| `звичайний` (default) | Canned replies, points, rock-paper-scissors, coffee / push-up / "gato" stats, and AI replies (`gpt-5-mini`) when someone talks to the bot |
| `бухгалтер` (accountant) | Points only: reply to a message with a number to give its author points, `@<bot> баланс`, and removal requests |
| `тихий` (quiet) | Silent; answers commands only |
| **Камертон** | Music reviews: share a `music.youtube.com` link, reply to it with a score from 1 to 10 (as text, a voice message or a video note), and get tops, stats, taste matches, achievements and a daily 09:00 reminder about unrated releases. Release metadata comes from YouTube oEmbed and Discogs |
| **Замітки** | Notes on demo audio: post an mp3/wav/flac, and replies to it are saved as notes on that version of the track |

Video notes are transcribed with Whisper and classified from extracted frames,
so production needs `ffmpeg`.

The full command list lives in the bot itself: send `@<bot> рятуй` (or
`@<bot> help`) in a chat. It's generated by
[`Response::Help`](app/services/response/help.rb) from the chat's current mode
and features, and a spec keeps it in sync with the commands.

## How an update flows

```
Telegram ──POST /telegram/webhook──▶ TelegramController
                                       │ checks X-Telegram-Bot-Api-Secret-Token
                                       ▼
                            TelegramUpdates::Ingest
                                       │ INSERT … ON CONFLICT (update_id) DO NOTHING
                                       │ enqueue ProcessTelegramUpdateJob, respond 200
                                       ▼
                            ProcessTelegramUpdateJob
                                       │ claims the row (one UPDATE), runs in a transaction
                                       ▼
                            TelegramUpdates::Dispatcher
                                       │ group chats only; reactions, migrations, /ping
                                       ▼
                                 MessageHandler
                    Camerton → Notes → Default / Accountant / Quiet handler
```

- **Duplicates are dropped.** `telegram_updates.update_id` is unique. A
  redelivered update that hasn't finished processing is enqueued again, and the
  job's claim decides whether it runs.
- **Jobs are safe to run twice.** The claim is a single conditional `UPDATE`,
  capped at 5 attempts. A run stuck in `processing` for more than 10 minutes
  is treated as dead and can be claimed again. Handler writes roll back if the
  reply fails to send.
- **Retries are selective.** Telegram 429/5xx, network timeouts, OpenAI
  connection or server errors, and deadlocks are retried with backoff. Anything
  else fails the job immediately, and the error is stored in
  `telegram_updates.last_error`.
- **The bot only acts in group chats.** Private messages and posts sent on
  behalf of a chat (anonymous admins, linked channels) are ignored.

Business logic lives in service objects under [`app/services/`](app/services),
not in controllers or model callbacks.

## Stack

- Ruby 3.3.12 (see `.ruby-version`), Rails 8.1, PostgreSQL
- Solid Queue for jobs, run inside Puma in async mode (no separate worker process)
- [`telegram-bot-ruby`](https://github.com/atipugin/telegram-bot-ruby) and the
  [`openai`](https://github.com/openai/openai-ruby) gem
- RSpec, FactoryBot, RuboCop (`rubocop-rails-omakase`), Brakeman, bundler-audit

## Running it locally

Requirements: Ruby 3.3.12, PostgreSQL, and `ffmpeg` if you want video notes
to work.

```bash
bundle install
bin/rails db:prepare
bin/rails server
```

Put the variables from [Configuration](#configuration) in a `.env` file at the
root. It's read by `dotenv-rails` in development and test, and git ignores it.
Development connects to `gatylnia_bot_development` as `postgres` with an empty
password. You can override that with `DB_USERNAME`, `DB_PASSWORD` and
`POSTGRES_DB`.

Telegram only delivers updates to a public HTTPS URL, so to talk to a local
server you need a tunnel (ngrok, cloudflared, …). Point
`TELEGRAM_WEBHOOK_URL` at it and register the webhook (see below). In
development, jobs use Active Job's default in-process adapter, so nothing
else needs to run.

## Configuration

| Variable | Required | What it's for |
|---|---|---|
| `TELEGRAM_BOT_API_TOKEN` | yes | Bot token from @BotFather |
| `BOT_USERNAME` | yes | The bot's username, used to spot `@mentions` |
| `TELEGRAM_WEBHOOK_SECRET` | yes | 32–256 chars of `A-Za-z0-9_-`. Telegram sends it with every update, and the controller rejects requests without it (it also returns 401 when the variable isn't set) |
| `TELEGRAM_WEBHOOK_URL` | for webhook tasks | Public URL of `/telegram/webhook` |
| `OPENAI_API_KEY` | yes | AI replies, classifiers, Whisper transcription |
| `DISCOGS_TOKEN` | no | Raises the Discogs rate limit from 25 to 60 requests a minute |
| `DATABASE_URL` | production | Postgres connection |
| `RAILS_MAX_THREADS` | no | Puma threads (default 3) |

### Registering the webhook

The bot must be an admin in the chat to receive reaction updates.

```bash
bin/rails telegram:configure_webhook   # set the webhook with the secret and allowed update types
bin/rails telegram:reset_webhook       # drop pending updates, then register again
```

## Tests and checks

```bash
bundle exec rspec                         # needs a local Postgres (gatylnia_bot_test)
bin/rubocop
bin/brakeman --no-pager
bin/bundler-audit
```

Specs never reach the network. Telegram is replaced by a fake client
(`spec/support/fake_telegram_client.rb`), and an unstubbed YouTube or Discogs
request raises. The suite is request specs plus model, job and service specs,
with no controller specs.

CI ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)) runs the
security scans, lint and tests on every pull request and on every push to
`main`.

## Deployment

Production runs on Heroku (app `gatylnia`) as a single web dyno.

- **Every green push to `main` deploys automatically.** CI's `deploy` job
  pushes to Heroku's git remote, one deploy at a time.
- **Migrations run in the release phase** (`release:` in [`Procfile`](Procfile)).
- **Jobs run inside the web dyno.** Solid Queue is a Puma plugin in async
  mode, and its threads share one 12-connection pool with Puma. Fork mode used
  to push the 512 MB dyno into R14 memory errors.
- **The deploy is verified.** [`bin/post-deploy-check`](bin/post-deploy-check)
  confirms that the release succeeded, the Solid Queue worker started, `/up`
  returns 200 and `ffmpeg` runs on a dyno, and that no R10/R14/H10 errors or
  crashes show up afterwards. If any of these fail, the CI run turns red.
- **Scheduled jobs** ([`config/recurring.yml`](config/recurring.yml)): hourly
  cleanup of finished Solid Queue jobs, daily deletion of finished Telegram updates
  older than 30 days at 04:00 UTC, and Camerton reminders at 09:00 Kyiv time.

The Dockerfile and Kamal config (`config/deploy.yml`, `.kamal/`) are leftovers from the Rails generator and
aren't used.

## Maintenance tasks

One-off data tasks. They're dry runs unless `DRY_RUN=0`, and each task's
source has a usage example.

| Task | What it does |
|---|---|
| `camerton:import_history` | Import Camerton shares and text reviews from a Telegram HTML export |
| `camerton:import_ratings` | Import one member's scores from a ratings spreadsheet (as JSON) |
| `camerton:discogs_backfill` | Look up Discogs genres, styles and years for releases never checked (imported ones) |
| `camerton:merge_duplicate_releases` | Merge releases that are the same song or album |
| `gato:import_history` | Rebuild a chat's gato entries for a time range from an HTML export |
| `chats:negate_pre_supergroup_ids` | Fix message numbers from before a group became a supergroup |
